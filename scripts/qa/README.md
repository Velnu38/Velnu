# Finviant infrastructure assessment

`target.json` pins this campaign to staging `xvybcmyoblfgzokaifsx`. The publishable key is a public client key; no service-role credential is stored or required. The isolated table is `public.finviant_qa_profiles`. It permits SELECT of synthetic fixtures and denies all browser writes. No real business/customer tables are seeded.

`node scripts/qa/generate-profiles.mjs --write` generates a full alternative reproducible 1,000-profile fixture set, plus `mock-profiles.json` and `seed-staging.sql`. These generated outputs can be reproduced locally and are excluded from Git to avoid duplicating the fixture generator. The deployed dataset was seeded with the first 100 generated profiles and expanded by the recorded `seed-additional-staging.sql` query. Live profiles are authoritative for campaign execution; their SHA-256 digest is in the log. Never seed this table on production. The table definition is in `schema-staging.sql`.

Run `npm ci`, then `node scripts/qa/stress-engine.mjs --seconds=14400 --phase=1 --interval=300`. Phase two uses `--phase=2 --resume=true`. A quick live check uses `--seconds=0 --edge-count=1` and still exercises all 1,000 profiles. The runner never silently uses local fixtures when the live dataset is unavailable.

The GitHub workflow runs two consecutive four-hour jobs because hosted jobs have a six-hour maximum. It queries the live dataset every five minutes, executes 100 scenarios per application function each cycle, and probes 12 staging Edge Function boundaries with 100 calls each at the start. Edge calls have no valid user session, operator token, customer approval token or provider signature; rejection is the expected result. Status 503 means a release/configuration gate, not healthy provider delivery. Frontend service success/error paths use the actual bundled app code with a simulated database transport. A BigInt cents oracle checks returned financial contracts; it does not independently prove live database accounting calculations.

The separate browser job runs the existing Playwright flows on a GitHub runner and uploads JSON results. Phase two merges browser errors into `STRESS_TEST_LOGS.json`. Browser fixtures mock Supabase. No live customer emails, payments, provider tokens or paid AI operations are used.

`publish-results.mjs` writes both required files to this same branch after each phase. The GitHub token comes only from the runner and is never written to a log. Logs record unexpected errors, per-function attempts, expected validation rejections, dataset digest, API response counts and measured campaign duration. Expected validation rejection is a pass; an unexpected TypeError, malformed response, API timeout or assertion failure is an error. A failure is never rewritten as a pass. If an infrastructure run is interrupted or cannot reach staging, the log/report must retain that limitation.
