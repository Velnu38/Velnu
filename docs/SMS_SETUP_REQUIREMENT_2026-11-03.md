# Owner mobile verification at SMS setup

Signup continues to require email/password; no cellphone field or SMS requirement is added to account creation. The primary business owner opens **Settings → Text messaging setup** when preparing to use texting. They enter an SMS-capable mobile, request a code and confirm it. A six-digit code uses the account's native Supabase Auth `phone_change` flow. Verification associates the number with that account, independently of the business contact printed on invoices, the customer recipient number, and the configured Twilio sender. Existing administrator authenticator requirements are unchanged.

The server reads Auth's confirmed-phone timestamp and phone field for the signed-in primary owner, together with verified email and the current owner authorization. Editable user metadata and client claims never grant verification. The status response exposes only a boolean and the last four digits of a confirmed number. The feature does not separately persist an OTP, raw phone or verification secret in an application table, extra browser storage or logs. Supabase’s existing authentication-session storage can contain the signed-in user’s phone, as part of its normal user/session data. The client verifies the successful Auth response belongs to the same user and requested number, then re-reads server state. Sending remains locked until those checks pass. An existing verified account mobile can satisfy setup.

The existing private SMS delivery test also enforces this rule: its server endpoint rejects an unverified owner, and a database insert trigger independently blocks a new SMS operation without confirmation. Existing retries, sender configuration, approved test recipients and explicit recipient permission still apply. Stripe tests remain available independently. The setup page never sends a customer document or enables customer messaging by itself.

A 60-second client cooldown and immediate in-flight guard prevent accidental duplicate requests. Auth's provider-side rate limits remain authoritative. Wrong/expired codes retain the fields for correction. A missing SMS provider produces a setup-needed message rather than claiming verification. Actual OTP delivery requires configured Auth SMS credentials. The public Auth settings currently report phone authentication disabled; the setup screen detects this and disables code requests with a setup-needed message. Email confirmation is already required. Mobile formatting plus a received code proves SMS reachability/control, not a legal identity or a carrier classification; the messaging provider's separate sender/business-registration requirements must also be completed. No real phone was enrolled or text sent during automated validation.

Validation includes the actual schema and caller/primary-owner checks, metadata and JWT-spoof denial, direct RPC send denial, unchanged non-SMS tests, client number formatting, desktop/mobile verification flows, wrong-code recovery, duplicate request prevention and a missing-provider state. Real code delivery and production customer texting are separate live checks, pending provider configuration.
